Rosette is a complex codebase that contains a high level of complexity. Before we dive into specifics, understanding my philosophy behind why I wrote Rosette in the way I did matters.

1. This project was purposefully written on macOS 13.7.5. My reasoning behind this is that providing support for older hardware means that Rosette will work for most Apple users. My OS'ses version of Rosetta 2 does not have AVX instructions, and thus, it allows me to check whether or not this support has genuinely occured easier. 

2. Writing this project in Zig was done for a number of reasons. One of these is the types of abstractions you can do. For example, you can make variables take on a compiler-time defintion of value, meaning that if you are working with getying Windows code to work on macOS, it is often useful to have them take on shared data. Another is that inheritence is much easier compared to doing this in C. If you need macOS to inherit a hardcoded value from Windows, you can ensure that Windows is properly stored under a Window's certifiable absolute data and make macOS inherit the value if there is a conflict. This cross-compilation benefit makes Zig an excellent choice, given how Assembly heavy this entire project is.

3. While libraries are useful, only integral pieces of code that would be too hard to recreate are included. The four third party libraries included are NASM, FASM, JWASM, and YASM. These are 4 Assemblers that can run in x86 on macOS. While the overhead may be about 15MB, that is a worthy amount given that I do not want to just emulate the basic functionality of these Assemblers. 

4. Shims/stubs are prefered to over the inclusion of headers. Whilst supporting Windows applications is just a fun side-effect of getting x86 to work (since it's a great testing ground for x86 instructions), this means that for anything Windows based, only shims of open-source implementations of a header is permitted. The aim is full DBT functionality, which means this will help interprate Windows behaviors not substantiated. 

5. An ABI validation layer helps ensure that platform definitions and translations do not drift in terms of logic. This allows for behaviors to be polled, and when there is a discrepancy, the user can recieve an abort trap. For example, one of the ways we do this is that before and after each function call, we check the values inside register. Whilst not as simple as just checking the registers (because how do you know what Windows is supposed to be is really what it is supposed to be?), a handshake process like this ensures that potential bugs are significantly reduced.
