A very critical part of disassembling code is when we get to TOML files. If we are unable to correctly parse these files, what ends up happening is that the Itanium unwinder is triggered because of a terminal import/cxxopt/C++ exception. This becomes a major problem in trying to diagnose the problem, because we cannot solve what we cannot see. 

This means that the process of dealing with this is to be able to see these files, decode/disassemble what is contained within, and what are the lines that trigger this fatal issue. Whilst some of it does come down to an issue of decoding, the most integral part of the architecture is being able to see completely under the hood to any and all processes that may cause us issues. 

Projects that do not rely upon TOML files will not have to worry, however, the biggest challenge will be how to handle assembled .exe and .app bundles that do contain this, that may introduce an issue of trying to hunt down where these are in the assembled application.

What is important about the disassembly is the point for real assembly, see if what you get back is properly interpreted. Since often TOML files are the culprit in parsing tokens incorrectly, that means it is better to take in what the file is trying to do since solving this has been extremely difficult. The idea is that you find the file within the Mach-O container and try to parse the text inside of the file, as a way of avoiding the issue of changes to UI breaking TOML handing. So in order to do this, the idea is disassembling how the TOML file works, and how we can get all its tokens, and treat the code correctly. Doing this disassembly and reassembly is better than the headache of something going wrong in the pipeline and then messing up how we parse TOML files.
