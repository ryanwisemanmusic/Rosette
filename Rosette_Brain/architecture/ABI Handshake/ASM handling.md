One of the most difficult parts of ensuring x86 accurately translates is ensuring that we have a simulated Windows layer to check against. For example, if we are doing a bunch of math operations on a register, we need to have some means of ensuring that our results are the same. In order to do this, this means we need a simulated Windows environment to compare things against. Given that programs often want to execute millions of instructions per second, any math errors can cause a critical issue, an issue I'll call drift. 

In order to prevent this, you must think of macOS and Windows doing their own work and needing a handshake to verify that, "Okay, we are on the same idea of what this operation equals". And in order to check this, you want to allow instructions to head out two two locations, NEON and a simulated x86 environment. Once they are done doing work, they report back to a centralized bridge. Since both can lead to a different appearance in results even if it is the same conclusion, it is important we have the ability to normalize what both NEON and x86 concluded, and have the ability to compare these. Once you get drift, it is important to send the user an abort trap. This is so that anything that is off, must receive immediate attention when this is encountered. 

However, it isn't just a matter of ensuring that your math is correct, but that the locations in which data is placed is able to also be analyzed. That too needs to be the subject of an ABI handshake validation. The same process happens but instead of this being about the results of instructions, this is about the results stored in registers. When we normalize everything so macOS and Windows are speaking the same language, we are able to compare the values and see if they align, else, send the user an abort trap.

However, the power of checking registers needs to be done at the most optimal places. Which means that we check the contents of these registers before and after each function call. Given that Zig is used as the primary language and how fast it is at code execution, this is perfect for a task that is invoked billions of times.
